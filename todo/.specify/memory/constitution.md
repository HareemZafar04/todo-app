# Evolution of Todo Constitution

## Core Principles

### I. Spec-Driven Development (Mandatory)
Spec-Driven Development (SDD) is MANDATORY for all work. No agent may write code without approved specifications and tasks.

The lifecycle MUST be strictly followed in order:
1. **Constitution** → Defines principles and constraints
2. **Specify** → `/sp.specify` creates feature specifications
3. **Plan** → `/sp.plan` creates architecture decisions
4. **Tasks** → `/sp.tasks` creates testable implementation tasks
5. **Implement** → `/sp.implement` executes tasks and generates code

Code generation is allowed ONLY at the `/sp.implement` stage. Any work outside this sequence is prohibited.

### II. No Manual Coding by Humans
Human manual coding is NOT permitted under ANY circumstance. All code must be generated by agents following the SDD lifecycle. Humans provide intent, specifications, and approval; agents produce implementation.

### III. No Feature Invention or Assumption
Agents MUST NOT invent features, assume requirements, or deviate from approved specifications. If ambiguity exists, the agent MUST request specification clarification before proceeding. Clarifications must be encoded back into the specification, not handled ad-hoc in code.

### IV. Strict Phase Isolation
Each phase is strictly scoped by its own specification:
- **Phase I** — Python Console Application (SQLite, TextUI)
- **Phase II** — Web API (FastAPI, SQLModel, Neon DB)
- **Phase III** — Next.js Frontend (Dashboard)
- **Phase IV** — AI Chatbot (OpenAI Agents SDK, MCP)
- **Phase V** — Deployment (Docker, Kubernetes, Kafka, Dadr)

Future-phase features MUST NOT appear in earlier phases. Architecture evolution is allowed only through updated specs and plans. Phase I must remain fully independent of later phases.

### V. Specification-First Refinement
All refinements, changes, and clarifications must occur at the specification level. Code is a consequence of specification, not a starting point. When code needs to change, the specification must be updated first.

### VI. Explicit Ambiguity Resolution
When requirements are unclear, agents MUST ask targeted clarifying questions (2-3 maximum) and wait for resolution before proceeding. Ambiguity resolved through conversation must be documented in the specification.

## Phase Governance

### Phase Scope Enforcement
- Each phase's specification defines its boundaries explicitly
- Out-of-scope items MUST be listed in every specification
- Cross-phase dependencies require explicit architectural review
- Phase I delivers a complete, working console application

### Technology Stack by Phase
| Phase | Technology | Purpose |
|-------|------------|---------|
| I | Python, SQLite, argparse/click | Console application |
| II | FastAPI, SQLModel, Neon DB | REST API backend |
| III | Next.js, Tailwind CSS | Frontend dashboard |
| IV | OpenAI Agents SDK, MCP | AI chatbot interface |
| V | Docker, Kubernetes, Kafka, Dapr | Production deployment |

### Backward Compatibility
- Each phase produces artifacts usable independently
- Phase II extends Phase I (same data model, evolved interface)
- Phase III extends Phase II (same API, new UI)
- Phase IV extends Phase III (same app, new interaction mode)
- Phase V containerizes and deploys Phase IV

## Quality Principles

### Code Quality Standards
- Minimum 80% test coverage for all new code
- All functions must have docstrings
- Type hints required for all Python code
- Linting must pass before commit

### Testing Requirements
- Unit tests for all business logic
- Integration tests for all API endpoints
- E2E tests for all user-facing workflows
- Tests must be auto-executable via `pytest`

### Security Standards
- No hardcoded secrets; use `.env` files
- Input validation on all external boundaries
- Authentication required for all non-Phase-I endpoints
- Audit logging for all data mutations

### Performance Budgets
- API response time: p95 < 200ms
- Page load time: < 2 seconds
- Database queries: < 50ms average
- Cold start (API): < 5 seconds

## Development Workflow

### Required Artifacts Per Feature
Every feature must produce, in order:
1. `specs/<feature>/spec.md` — Requirements and acceptance criteria
2. `specs/<feature>/plan.md` — Architecture and interface design
3. `specs/<feature>/tasks.md` — Implementation steps with test cases
4. Code implementation (via `/sp.implement`)
5. Tests passing

### Artifact Location Standards
- Specifications: `specs/<feature>/`
- Plans: `specs/<feature>/plan.md`
- Tasks: `specs/<feature>/tasks.md`
- ADRs: `history/adr/`
- PHRs: `history/prompts/`

### Review Gates
- Spec review required before planning
- Plan review required before tasking
- Task review required before implementation
- Test pass required before merge

## Governance

### Constitution Supremacy
This constitution SUPERSEDES all other practices and guidelines. Any conflict between this constitution and other documents must be resolved in favor of this constitution.

### Amendment Process
Constitution amendments require:
1. Documentation of proposed change
2. Rationale and impact analysis
3. User approval
4. Migration plan for existing artifacts

### Compliance Verification
All code reviews, PHR reviews, and quality gates MUST verify compliance with this constitution. Non-compliant work must be rejected and corrected.

### Version Control
- Major version: Structural changes to the constitution
- Minor version: New principles or phases added
- Patch version: Clarifications, corrections
